Static routing has two major flaws: you have to **write everything by hand**, and it **doesn't react
to failures**. A dynamic routing protocol solves both: routers share what they know, build their table
themselves and recompute it when the network changes.

## The problem with static routing

Take a ring of four routers. With static routing, R1 has a route to headquarters via R2. If the R1-R2
link fails, the route stays in the table… and traffic goes nowhere, even though another path exists
through R4.

You could add floating routes everywhere, but the number of combinations explodes as the network grows.
A dynamic protocol recomputes everything automatically within seconds.

## What a routing protocol does

Whatever the protocol, you find the same steps:

1. **Discover neighbors**: directly connected routers speaking the same protocol.
2. **Exchange information**: the known networks, and at what "price".
3. **Compute the best path** to each network.
4. **Install** these routes in the routing table.
5. **Monitor**: if a neighbor disappears or a link changes, compute again.

## Control plane and data plane

A router does two very different jobs, which are kept clearly separate:

- The **control plane**: the protocols, the calculations, the <Term id="rib" />. It runs on the
  router's CPU and takes its time.
- The **data plane**: forwarding each packet, using the <Term id="fib" />, a copy of the best routes
  programmed into specialized chips. It handles billions of packets per second.

<Callout type="tip">
This separation explains a lot: a router whose CPU is maxed out can keep forwarding traffic, and a route
visible in `show ip route` but missing from the hardware is a real failure case (known as RIB and FIB
being out of sync).
</Callout>

## IGP and EGP

Protocols are first classified by **where** they are used:

- an **IGP** (<Term id="igp" />) works **inside** an organization, within a single **autonomous
  system** (<Term id="as" />). Goal: find the fastest path, converge quickly. Examples: OSPF, IS-IS,
  (EIGRP, RIP).
- an **EGP** works **between** organizations. Goal: apply **policies** (who may go through whom, at
  what commercial price), at Internet scale. Only one is left: **BGP**.

## Three protocol families

### Distance vector: "routing by rumor"

Each router sends its **routing table** to its neighbors: "I know such network, at such distance".
The neighbor adds 1 and passes it on. Nobody has the big picture: you believe what your neighbors say.
This is how **RIP** works.

Simple, but **slow**: bad news spreads from neighbor to neighbor, and temporary loops can appear. RIP
has all but disappeared from enterprise networks.

### Link state: everyone has the full map

Each router describes **its own links** ("I am R1, connected to R2 with a cost of 10") and floods this
description **to every router** in the area. Each one thus gets the **full map** of the network,
identical everywhere, and computes the shortest path itself with **Dijkstra's** algorithm (SPF,
*Shortest Path First*). This is how **OSPF** and **IS-IS** work.

More computation for each router, but **fast** and **loop-free** convergence, since everyone works on
the same map. This is the family of modern IGPs.

### Path vector: BGP

**BGP** looks like distance vector (you advertise networks to your neighbors), but instead of a simple
distance, each route carries **the list of ASes it went through** (the AS_PATH) and many other
attributes. This list prevents loops (an AS rejects a route that already contains its own number) and
allows very fine-grained **policies**. Chapters 3 to 5 are dedicated to it.

| Family | Principle | Protocols | Where |
|---|---|---|---|
| Distance vector | you pass your table to your neighbors | RIP, (EIGRP) | legacy |
| Link state | everyone has the full map and computes | **OSPF**, **IS-IS** | internal networks, ISPs, data centers |
| Path vector | you pass routes with the list of ASes | **BGP** | Internet, interconnections, EVPN fabrics |

## The metric

To decide between several paths to the same destination **within one protocol**, each one uses its
**metric**:

- RIP counts **hops**, ignoring bandwidth: it will prefer 2 hops at 10 Mb/s over 3 hops at 10 Gb/s;
- OSPF uses a **cost** tied to link bandwidth: the faster the link, the lower the cost;
- BGP has no single metric, but a **list of attributes** compared in a precise order.

And between **two different protocols** offering the same destination? The **administrative
distance**, seen in the static routing chapter, decides: for an equal prefix, the most trusted source
wins (static 1, eBGP 20, OSPF 110 on Cisco). The **longest prefix** rule still takes priority over
everything else.

<Callout type="warning">
Never compare an OSPF metric with a BGP metric: they have nothing in common. The full decision order
is: 1) the longest prefix, 2) the lowest administrative distance, 3) the best metric, within the chosen
protocol.
</Callout>

## Convergence

**Convergence** is the time between a change (a link going down) and the moment **all** routers have a
consistent table. During that time, traffic can be lost. It breaks down into:

1. **detecting** the failure: immediate if the physical link goes down, several seconds if you wait
   for the neighbor to stop answering (hence the value of **BFD**, which detects a failure in under a
   second);
2. **propagating** the information to the other routers;
3. **recomputing** the best paths;
4. **updating** the FIB in hardware.

<Callout type="field">
In production, protocol timers themselves are rarely tuned. Instead, **BFD** is enabled on important
links: detection drops from 40 seconds (OSPF's default dead interval) to a few hundred milliseconds, and
everything else follows.
</Callout>

## Key takeaways

- Dynamic routing **discovers** neighbors, **exchanges** routes, **computes** and **reacts** to failures.
- **IGP** inside an AS (OSPF, IS-IS), **EGP** between ASes (BGP).
- **Link state**: each router has the full map and computes the shortest path (Dijkstra).
- Decision order: **longest prefix**, then **administrative distance**, then **metric**.
- The **control plane** (RIB, computation) and the **data plane** (FIB, forwarding) are separate.
