With Python, you write **how** to do things: connect, type this command, read the output. With
**Ansible**, you describe **what you want to end up with** ("these VLANs must exist on these leafs") and
Ansible compares it with what is there and applies only the difference. It is the most widespread tool for
automating an enterprise network.

## How Ansible works

- **Agentless**: nothing to install on the devices. Ansible runs on a **control node** (your machine, a CI
  runner) and connects over SSH or through an API.
- **An inventory** lists the devices and groups them.
- **Playbooks** written in YAML chain **tasks**; each task calls a **module**.
- **Collections** provide each vendor's modules: `arista.eos`, `cisco.ios`, `junipernetworks.junos`…

<Callout type="note">
On a Linux server, Ansible copies a small Python program to the machine and runs it. On a switch, that is
impossible: network modules therefore run **on the control node**, and the `network_cli` connection sends
the commands over SSH. That is what `ansible_connection` specifies.
</Callout>

## Idempotency

This is Ansible's central notion. An <Term id="idempotence">idempotent</Term> task describes a **state**:
it only changes the device if it is not already in that state. You can therefore run a playbook as many
times as you like, with no side effects.

The desired VLANs are described in a variables file, separate from the playbook:

<CodeFile lab="netops" file="ansible/vars/vlans.yml" />

<CodeFile lab="netops" file="ansible/vlans.yml" />

Before applying, ask Ansible what it **would do**, in simulation mode (`--check`). With `-v`, resource
modules display the list of commands they would send:

```text title="ansible-playbook ansible/vlans.yml --check -v (excerpt)"
TASK [Configurer les VLAN] *****************************************************
changed: [leaf1] => {"before": [{"name": "default", "state": "active", "vlan_id": 1}],
                     "commands": ["vlan 10", "name USERS", "vlan 20", "name GUEST-WIFI",
                                  "vlan 30", "name SERVERS"], ...}
```

Adding `--diff` also shows the before and after state. The exact layout varies with the collection version,
but the idea stays the same: you see **before** you apply.

| Run | Result | Why |
|---|---|---|
| `--check` | `changed`, but nothing is applied | simulation: you see the commands that would be sent |
| 1st run | `changed=1` on each leaf | the VLANs didn't exist, they are created |
| 2nd run | `changed=0` | the desired state is already reached: nothing to do |

<Callout type="tip">
`--check --diff` is the best reflex before any production change: it shows exactly what is going to
change. In a pipeline, run it on the merge request, and only apply after review.
</Callout>

## Modules to know

| Module | Role | Idempotent? |
|---|---|---|
| `eos_facts` | gather information (model, version, interfaces…) | read-only |
| `eos_command` | run `show` commands | read-only (in principle) |
| `eos_config` | send configuration lines, or a <Term id="jinja" /> template | yes, by comparing with the running-config |
| `eos_vlans`, `eos_interfaces`, `eos_l3_interfaces`, `eos_bgp_global`… | **resource modules**: describe a feature as data | yes, with `state`: `merged`, `replaced`, `overridden`, `deleted` |

**Resource modules** are the way to go: you handle data (a list of VLANs), not CLI lines, and the `state`
parameter says precisely what to do with what already exists. For example, `overridden` removes the VLANs
that are **not** in the list: the device becomes the exact reflection of the data.

## Protecting secrets: Ansible Vault

Our credentials come from environment variables. To store secrets alongside the code (passwords, TACACS+ keys,
SNMP communities), Ansible provides **Ansible Vault**, which encrypts with AES-256 using a password. Encrypted
content can be committed to Git: without that password, it is unreadable.

### The commands

| Command | What it does |
|---|---|
| `ansible-vault create file.yml` | creates an encrypted file and opens it in the editor |
| `ansible-vault edit file.yml` | decrypts in memory, opens the editor, re-encrypts on close |
| `ansible-vault view file.yml` | shows the decrypted content, without writing anything to disk |
| `ansible-vault encrypt` / `decrypt file.yml` | encrypts or decrypts an existing file, in place |
| `ansible-vault encrypt_string 'value' --name variable` | encrypts a single value, to paste into a plain variables file |
| `ansible-vault rekey file.yml` | changes the password of an encrypted file |

### A whole file, or a single variable

You can encrypt **a whole** variables file, or **a single value** with `encrypt_string`:


The second approach keeps the rest of the file readable, along with its diffs in Git. For a whole file, the
convention is to separate secrets from their use:

```yaml title="group_vars/eos/vault.yml (encrypted)"
vault_tacacs_key: s3cr3t
```

```yaml title="group_vars/eos/vars.yml (plain)"
tacacs_key: "{{ vault_tacacs_key }}"
```

A `grep tacacs_key` on the repository then finds the variable, and the `vault_` prefix tells you where it is
defined.

### Several vaults: vault IDs

The same password for the lab and production means giving production to everyone who touches the lab. **Vault
IDs** (`--vault-id label@source`) let you use one password per environment. The label is written in the encrypted
content's header (`$ANSIBLE_VAULT;1.2;AES256;prod`), and a playbook can receive several:

```bash
ansible-vault encrypt --vault-id dev@~/.vault/dev.pass group_vars/lab/vault.yml
ansible-vault encrypt --vault-id prod@~/.vault/prod.pass group_vars/prod/vault.yml
ansible-playbook site.yml --vault-id dev@~/.vault/dev.pass --vault-id prod@prompt
ansible-vault rekey --vault-id prod@~/.vault/prod.pass --new-vault-id prod@prompt group_vars/prod/vault.yml
```

The source is a password file, or `prompt` to type it. With a wrong password, the message is explicit:

```text title="ansible-vault view with a wrong password"
[ERROR]: Failed to view 'dev.yml': Decryption failed (no vault secrets were found that could decrypt).
```

### Where to keep the vault password

- **On a workstation**: a file outside the repository, readable only by you (`chmod 600`), given with `--vault-id`
  or the `ANSIBLE_VAULT_PASSWORD_FILE` variable. Add its name to `.gitignore` as a precaution.
- **In a GitLab pipeline**: a masked, protected variable of type **File**. GitLab writes its content to a temporary
  file and puts the **path** in the variable: `--vault-id prod@$VAULT_PASS_PROD`.
- **Never** in the repository, nor in `ansible.cfg`, nor as a command argument visible in the shell history.

### The trap: a re-encrypted secret… written in clear text

<Callout type="warning">
The `ansible.builtin.vault` filter encrypts a value in a template. But that encryption doesn't always survive being
written: with ansible-core 2.21, a value passed through this filter and then written with `copy` and `content:` is
**decrypted** at write time, and the file holds the secret **in clear text**. The playbook finishes without any
error. To produce an encrypted file, go through `ansible-vault` itself, and check the result.
</Callout>

```yaml title="Writing an encrypted file, then checking it really is"
- name: Encrypt with ansible-vault, the content going through standard input
  ansible.builtin.command:
    cmd: ansible-vault encrypt --vault-id prod@{{ vault_pass_file }} --output {{ secrets_file }} -
    stdin: "{{ new_secrets | to_nice_yaml }}"
  no_log: true
  changed_when: true

- name: Read the file as it is on disk (slurp doesn't decrypt)
  ansible.builtin.slurp:
    src: "{{ secrets_file }}"
  register: written

- name: Check that the written file is really encrypted
  ansible.builtin.assert:
    that: (written.content | b64decode).startswith('$ANSIBLE_VAULT')
    fail_msg: "{{ secrets_file }} is not encrypted: don't commit it"
```

For the check, use `slurp`, not the `file` lookup: the latter automatically **decrypts** an encrypted file whose
password it knows, and the test would fail on a file that is actually fine.

### Good practices

- **No secret in clear text in Git**, even in a private repository: a repository always ends up cloned, copied or
  made public. A secret committed by mistake is compromised: change it, cleaning the history isn't enough.
- **One vault per environment** (lab, staging, production), with different passwords.
- **Least privilege**: the playbooks' service account only has the rights it needs.
- **`no_log: true`** on every task handling a secret, so it shows up neither in the output nor in the logs.
- **Rotation**: `rekey` the vault when someone who knew its password leaves, and change the secrets themselves if
  they could read them.

Ansible Vault remains a file protected by **a single shared password**, with no record of who read it. Chapter 4
moves on to a real secrets vault, **HashiCorp Vault**, with per-person permissions and a log of every read.

## Python or Ansible?

| | Python | Ansible |
|---|---|---|
| Approach | imperative: you write the steps | declarative: you describe the desired state |
| Idempotency | up to you to program | provided by the modules |
| Complex logic, computations, various APIs | very comfortable | quickly tedious |
| Readability for the team | requires coding skills | YAML everyone can read |
| Typical use | custom tools, data collection, integrations | configuration deployment, repetitive operations |

The two complement each other: many teams deploy with Ansible and write the surrounding tools in Python
(reports, checks, NetBox integrations). The next two chapters provide each script in both versions.

## Key takeaways

- Ansible is **agentless**: for networking, modules run on the control node (`network_cli`).
- **Inventory** + **group_vars** + **playbooks**; **collections** provide the vendor modules.
- **Idempotency**: describe a state, apply only the difference; `--check --diff` before applying.
- Prefer **resource modules** and their `state` parameter.
- Secrets go in **Ansible Vault** (or a real vault), never in clear text in the repository: one vault per
  environment with `--vault-id`, and a check that every written file starts with `$ANSIBLE_VAULT`.
