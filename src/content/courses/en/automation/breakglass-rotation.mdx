On many networks, people still log into devices with **the same local account for everyone**, often named
`admin`, with a password that hasn't changed in years. It is one of the most common weaknesses, and one of
the easiest to fix. This chapter puts the good practice in place, and automates it.

## Why the shared admin account is a problem

- **Its name is known**: `admin`, `cisco`, `root`… Bots scanning the Internet and attackers already inside
  the network try these accounts first. All that is left is guessing the password.
- **Its password is shared**: everyone knows it, it travels in files, messages and documentation.
- **There is no traceability**: when `admin` deleted a VLAN at 3 am, there is no way to know who was behind
  it.
- **It survives departures**: a colleague who leaves the company still knows it. Changing it by hand on
  hundreds of devices is something nobody really does.

## The target model

Three uses are clearly separated:

| Use | Account | Where it is defined |
|---|---|---|
| Engineers' daily work | a **named account** per person, with MFA | <Term id="tacacs" /> or RADIUS server (<Term id="aaa" />) |
| Automation (backups, deployments) | a **service account** with limited rights | TACACS+ server |
| Last resort, if the AAA servers are unreachable | **one local break-glass account**, with a password **unique to each device** | on the device, password in a **vault** |

On the device side, the AAA configuration relies on TACACS+ and only falls back to **local** accounts if no
server answers:

```text title="Arista EOS: TACACS+ first, local accounts as fallback"
tacacs-server host 192.0.2.50 key <shared-key>
tacacs-server host 192.0.2.51 key <shared-key>
!
aaa group server tacacs+ TACACS
   server 192.0.2.50
   server 192.0.2.51
!
aaa authentication login default group TACACS local
aaa authorization exec default group TACACS local
aaa authorization commands all default group TACACS local
aaa accounting commands all default start-stop group TACACS
```

<Callout type="note">
`local` is only consulted if **no TACACS+ server answers**. A user rejected by TACACS+ is not retried
locally: a former colleague whose TACACS+ account was deleted therefore cannot fall back on a local
account… provided they don't know one. Hence the importance of a unique break-glass account and its
rotation.
</Callout>

## Break-glass account rules

1. **A name that can't be guessed**, specific to the company, never `admin`. The lab uses `nh-breakglass`.
2. **A long, random password** (32 characters), **different on each device**: a compromised password
   opens only one door.
3. **Nobody knows it by heart**: it is generated by a script and stored in a **vault**,
   [HashiCorp Vault](/en/courses/automation/vault), where every access is logged.
4. **Regular rotation**: **every 4 months**.
5. **Immediate rotation**:
   - when **a team member leaves** who had access to the vault;
   - **after each use** of the account (the password has been seen);
   - at the slightest suspicion of compromise.

## Removing the admin account… without locking yourself out

Removing `admin` first means risking losing all access if the break-glass account doesn't work. The
**order of operations** is therefore essential, and our scripts follow it strictly:

Three precautions make the operation safe:

- **The password is stored in the vault before being applied** (step 2). If the script crashes right after
  changing a device, the new password is not lost: it is the latest version of the secret in Vault, with the
  `pending` status. And if the device was not changed, the old password is the previous version.
- **Verification uses an independent connection**, with the new password. Seeing that the command went
  through is not enough.
- **One device at a time**: if something goes wrong on the first one, the others are untouched.

## The vault: HashiCorp Vault

Passwords are stored in [HashiCorp Vault](/en/courses/automation/vault), KV v2 engine, with **one secret per
device**: `secret/netops/breakglass/<device>`. Each secret holds the account name, the password and a
**status**:

| Status | Meaning |
|---|---|
| `pending` | written just before changing the device: it may or may not have been applied |
| `active` | applied, verified by a new connection, configuration saved |

Each rotation therefore creates two versions per device, and Vault keeps the previous ones: the history shows
when each password changed, and who changed it.

```bash
vault kv get -field=password secret/netops/breakglass/leaf1   # the current password
vault kv metadata get secret/netops/breakglass/leaf1          # versions, their dates and authors
vault kv get -version=5 secret/netops/breakglass/leaf1        # a previous password
```

The script authenticates with the `netops-rotation` **AppRole**, whose policy only allows writing and reading
under `secret/netops/breakglass/`. Engineers only have read access, and each of their reads is logged: you know
who has seen the password, and therefore when it must be changed.

<Callout type="warning">
The break-glass account is used when the network is down: the vault must remain reachable at that moment. Make
Vault reachable through the out-of-band network, run it as a cluster, and keep an offline copy for the most
critical devices (see [the network trap](/en/courses/automation/vault#the-network-trap-the-vault-during-an-outage)).
</Callout>

## The Python version

The script goes through the `VaultClient` class introduced in the [previous chapter](/en/courses/automation/vault).

<CodeFile lab="netops" file="python/rotate_breakglass.py" />

```text title="python3 python/rotate_breakglass.py --remove-default-admin"
OK    spine1  (version 2)
OK    leaf1  (version 2)
OK    leaf2  (version 2)
Rotation terminée : les mots de passe sont dans Vault, sous secret/netops/breakglass/.
```

The script reports, in French, the new secret version for each device, then that the rotation is complete and
the passwords are in Vault. On failure, it stops and says which secret version matches which password: the
`pending` version (maybe applied), or the previous one, which the device kept if it was not changed.

## The Ansible version

The playbook follows the same steps, one device at a time (`serial: 1`), stopping at the first error
(`any_errors_fatal: true`). It writes to Vault with the `vault_kv2_write` module from the
`community.hashi_vault` collection.

<CodeFile lab="netops" file="ansible/rotate_breakglass.yml" />

A few important details:

- `no_log: true` stops Ansible from displaying passwords in its output and logs;
- `module_defaults` gives every Vault module the same connection: the `VAULT_TOKEN` token, or the AppRole if
  `VAULT_ROLE_ID` is set;
- the Vault tasks and the eAPI check run on the Ansible machine (`delegate_to: localhost`), not on the device;
- the password contains neither spaces nor `?` (which triggers the CLI help);
- verification goes through **eAPI** (`uri`): an HTTPS connection completely independent of the SSH session
  that just changed the configuration.

<Callout type="warning">
Configuration commands may be logged, by TACACS+ accounting (`aaa accounting commands`) or by syslog. EOS
stores a hash of the password in its configuration, but the typed command itself may appear in clear text
in those logs. Check how your AAA server handles these commands, and restrict access to the logs
accordingly.
</Callout>

## Automating: every 4 months and at every departure

The rotation runs in a pipeline, like the backup. Two triggers:

- a **schedule** every 4 months: `0 6 1 1,5,9 *` (January 1st, May 1st and September 1st at 6 am);
- a **manual** run from the interface (*Run pipeline*), the day a team member leaves.

```yaml title=".gitlab-ci.yml (rotation job, to add)"
# Add "security" to the list of stages: stages: [backup, security]
rotate-breakglass:
  stage: security
  image: python:3.12-slim
  rules:
    - if: $CI_PIPELINE_SOURCE == "schedule" && $JOB == "rotate-breakglass"
    - if: $CI_PIPELINE_SOURCE == "web"
  before_script:
    - pip install -q -r requirements.txt
  script:
    - python3 python/rotate_breakglass.py --remove-default-admin
```

The job no longer changes the repository: passwords live in Vault, not in Git. Variables to create (masked,
protected): `NET_USER`, `NET_PASSWORD`, `VAULT_ADDR`, `VAULT_ROLE_ID` and `VAULT_SECRET_ID`. Better still, the
JWT authentication described in the [previous chapter](/en/courses/automation/vault#using-vault-from-automation)
removes the last two. The schedule sets `JOB=rotate-breakglass`, so the rotation doesn't run alongside the
nightly backup.

### Checklist when a team member leaves

1. Disable their named account in the directory and on the TACACS+ server.
2. **Run the break-glass rotation pipeline**.
3. Their Vault access follows their directory account (OIDC or LDAP): it goes away with it. If they knew an
   AppRole `secret_id` or a token, revoke it and generate new ones for the pipelines.
4. Revoke their SSH keys, API tokens and GitLab access.
5. Review the TACACS+ accounting of their last weeks of activity.

## In the lab

1. Deploy the lab and check that the default account works: `ssh admin@172.20.30.12` (password `admin`).
   That is exactly the problem.
2. Point the scripts at the lab's Vault: `export VAULT_ADDR=http://172.20.30.70:8200`, then either
   `export VAULT_TOKEN=netops-root`, or, more realistic, the AppRole from the previous chapter
   (`export VAULT_ROLE_ID=… VAULT_SECRET_ID=…`).
3. Run the rotation (Python or Ansible) with admin account removal.
4. Check: `ssh admin@172.20.30.12` is rejected; `ssh nh-breakglass@172.20.30.12` works with the password
   read by `vault kv get -field=password secret/netops/breakglass/leaf1`.
5. Run the rotation again: the passwords change, the old one no longer works. Show the history with
   `vault kv metadata get secret/netops/breakglass/leaf1`.
6. Read the audit log: which reads and writes did the rotation make?
7. Bonus: stop leaf2 (`docker stop clab-netops-leaf2`) and run again. The script stops on leaf2: what is the
   status of its secret, and which password does it really have?

## Key takeaways

- The shared `admin` account is **known, shared, untraceable** and **survives departures**: remove it.
- Day to day: **named accounts** via TACACS+; as a last resort: **one local break-glass account**, with a
  name that can't be guessed and a password **unique to each device**, kept in **Vault**.
- Rotate **every 4 months**, and **immediately** when a colleague leaves or after each use.
- Order is vital: **create and verify the break-glass account before removing admin**, and store the new
  password in the vault **before** applying it (`pending`), then confirm it (`active`).
- Vault's **versions** keep the old password if something fails, and its **audit log** tells who read what.
- A scheduled pipeline that can also be triggered by hand makes rotation **systematic**, not heroic.
