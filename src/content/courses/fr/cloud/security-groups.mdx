Au chapitre précédent, on a vu que la route `local` relie tous les sous-réseaux d'un VPC : par défaut, rien
n'empêche une machine d'en joindre une autre. Le filtrage se fait à deux niveaux, avec deux outils très
différents : le **security group**, un firewall avec état collé à chaque interface, et la **NACL**, une liste
de contrôle d'accès sans état posée sur le sous-réseau. Bien les distinguer évite des heures de dépannage.

## Le security group : un firewall avec état sur chaque interface

Un **security group** (SG) s'attache à l'interface réseau d'une ressource (une machine, une base de données,
un load balancer), pas au sous-réseau. Ses règles ont quatre propriétés à connaître :

- **avec état** : si une connexion entrante est autorisée, sa réponse repart automatiquement, sans règle de
  sortie. C'est la [table de sessions](/formations/security/ngfw-basics) d'un firewall ;
- **uniquement des autorisations** : on ne peut pas écrire « refuser ». Ce qui n'est pas autorisé est refusé ;
- **pas d'ordre** : toutes les règles sont évaluées ensemble, la plus permissive l'emporte ;
- **cumulables** : une interface peut porter plusieurs groupes (cinq par défaut), leurs règles s'additionnent.

Un groupe nouvellement créé refuse toutes les entrées et autorise toutes les sorties.

<Callout type="note">
Terraform se comporte autrement que la console : quand il crée un security group, il **supprime** la règle de
sortie « tout autoriser » qu'AWS ajoute d'habitude. Le lab déclare donc ses règles de sortie explicitement.
C'est plutôt une bonne chose : chaque flux, même sortant, est une décision écrite.
</Callout>

## Référencer un groupe plutôt qu'une adresse

C'est la fonction qui change la façon de penser le filtrage. La source d'une règle peut être un **autre
security group** : « autoriser le port 8080 depuis tout ce qui porte le groupe `web` ». Peu importe les
adresses des serveurs web, leur nombre, ou qu'ils soient recréés chaque nuit par un autoscaling : dès qu'une
interface porte le groupe `web`, elle est autorisée.

Dans le lab, c'est exactement la règle du groupe `app` :

```hcl title="security.tf (extrait)"
resource "aws_vpc_security_group_ingress_rule" "app_from_web" {
  security_group_id            = aws_security_group.app.id
  description                  = "Application depuis les serveurs web"
  ip_protocol                  = "tcp"
  from_port                    = 8080
  to_port                      = 8080
  referenced_security_group_id = aws_security_group.web.id
}
```

<Callout type="tip">
Les groupes se nomment comme des rôles (`web`, `app`, `db`, `bastion`), jamais comme des adresses ou des
personnes. On retrouve la logique des objets d'un firewall vue au chapitre
[Politiques de sécurité](/formations/security/security-policies) : la règle décrit une intention, les membres
peuvent changer.
</Callout>

## La NACL : une ACL sans état sur le sous-réseau

La **Network ACL** (NACL) s'applique à tout le trafic qui **entre ou sort d'un sous-réseau**. Elle fonctionne
comme une <Term id="acl" /> de routeur :

- **sans état** : chaque paquet est évalué seul. Autoriser l'entrée vers le port 443 ne suffit pas, il faut
  aussi autoriser la **sortie** des réponses vers les ports éphémères du client (1024 à 65535) ;
- **des règles numérotées**, évaluées dans l'ordre croissant : la première qui correspond décide ;
- **autoriser et refuser** : c'est le seul endroit d'un VPC où l'on peut écrire un refus explicite ;
- **un refus implicite** final (la règle `*`).

La NACL par défaut d'un VPC autorise tout ; une NACL créée à la main refuse tout tant qu'on n'y ajoute rien.

| Règle (entrée) | Protocole | Ports | Source | Action |
|---|---|---|---|---|
| 100 | tous | tous | `10.50.0.0/16` | autoriser |
| 200 | TCP | 1024-65535 | `0.0.0.0/0` | autoriser (réponses aux sorties via la NAT Gateway) |
| `*` | tous | tous | `0.0.0.0/0` | refuser |

C'est la NACL des sous-réseaux privés du lab. La seconde règle illustre l'absence d'état : sans elle, les
machines privées pourraient envoyer leurs requêtes vers Internet, mais les réponses seraient jetées à
l'entrée du sous-réseau.

## Security group ou NACL ?

| | Security group | NACL |
|---|---|---|
| S'applique à | une interface | un sous-réseau entier |
| État | **avec état** | **sans état** (penser aux réponses) |
| Règles | autorisations seulement | autorisations et refus |
| Évaluation | toutes les règles ensemble | dans l'ordre des numéros, la première gagne |
| Source possible | adresse, préfixe ou **autre groupe** | adresse ou préfixe |
| Usage | **le filtrage fin, au quotidien** | des barrières grossières : bloquer une plage, isoler un niveau |

En pratique, le filtrage se fait dans les security groups, et les NACL restent proches du défaut, avec
quelques règles larges. Un paquet doit passer **les deux** : NACL du sous-réseau, puis security group de
l'interface, et le chemin inverse pour la réponse.

## Dépanner avec les VPC Flow Logs

Quand une connexion échoue, on ne peut pas brancher de sonde sur un VPC. Les **VPC Flow Logs** enregistrent
une ligne par flux, accepté ou refusé, au niveau d'un VPC, d'un sous-réseau ou d'une interface. Ils
s'envoient vers CloudWatch Logs ou S3, sans impact sur les performances. Le format par défaut, avec deux
exemples tirés de la documentation AWS :

Les champs, dans l'ordre : version, compte, interface, adresse source, adresse destination, port source,

<Callout type="field">
Une astuce de la documentation AWS pour savoir qui a refusé : si le flux entrant apparaît en `ACCEPT` mais
que la réponse sortante apparaît en `REJECT`, le coupable est une **NACL**, car un security group, avec état,
aurait laissé passer la réponse. Pour une analyse sans trafic réel, *Reachability Analyzer* calcule le chemin
entre deux ressources et désigne la règle qui bloque (chaque analyse est facturée).
</Callout>

## Les équivalents Azure et Google Cloud

| AWS | Azure | Google Cloud |
|---|---|---|
| Security group (interface, avec état, autorisations) | **NSG** : avec état, autorisations **et** refus, priorités numérotées, attachable au sous-réseau **ou** à l'interface | **Règles de firewall** du VPC : avec état, priorités, autorisations et refus |
| Référence à un autre groupe | **Application Security Group** (ASG) | **Tags réseau** ou **comptes de service** comme source et cible |
| NACL (sous-réseau, sans état) | pas d'équivalent séparé : le NSG sur le sous-réseau joue ce rôle | pas d'équivalent ; politiques de firewall hiérarchiques au niveau de l'organisation |
| VPC Flow Logs | Flow logs des VNet (via Network Watcher) | VPC Flow Logs |

## Dans le lab

1. Déployez le lab (`terraform apply`) et ouvrez *VPC > Security groups* : le groupe `nexthop-app` a une
   seule règle entrante, dont la source est l'identifiant du groupe `nexthop-web` (`sg-…`), pas une adresse.
2. Ouvrez *VPC > Network ACLs* : la NACL `nexthop-nacl-private` est associée aux deux sous-réseaux privés.
   Retrouvez ses règles 100 et 200 et la règle `*`.
3. Supprimez la règle 200 dans `security.tf`, faites un `terraform plan` : Terraform annonce la destruction
   d'une seule ressource. Rétablissez-la.
4. Activez les Flow Logs (`terraform apply -var enable_flow_logs=true`), et ouvrez le groupe de journaux
   `/vpc/nexthop/flow-logs` dans CloudWatch. Sans machine dans le VPC, il reste presque vide : pour voir du
   trafic, lancez une petite instance dans un sous-réseau public (et pensez à la supprimer).
5. En fin de séance : `terraform destroy`.

## À retenir

- Le **security group** est attaché à l'**interface** : **avec état**, autorisations seulement, toutes les
  règles évaluées ensemble.
- **Référencez des groupes** plutôt que des adresses : la règle survit aux changements d'adresses et à
  l'autoscaling.
- La **NACL** est attachée au **sous-réseau** : **sans état** (autoriser les réponses sur les ports
  éphémères), numérotée, avec des refus possibles.
- Filtrage fin dans les security groups, barrières grossières dans les NACL ; un paquet doit passer les deux.
- Les **VPC Flow Logs** montrent chaque flux accepté ou refusé : le premier outil de dépannage.
