Le parcours a commencé par un câble et une trame Ethernet. Il se termine là où vont aujourd'hui une bonne
partie des applications : dans le **cloud public**. Un réseau cloud se configure par une API plutôt qu'en
CLI, mais on y retrouve tout ce que les sauts précédents ont construit : un plan d'adressage, des tables de
routage, des firewalls, du BGP, des tunnels IPsec et du code versionné. Ce saut montre ce qui reste
identique, ce qui change vraiment, et comment relier proprement le cloud au data center.

## Le fil rouge : l'entreprise s'installe dans la région de Paris

L'entreprise des formations précédentes déploie ses nouvelles applications chez **AWS**, dans la région
`eu-west-3` (Paris). Le réseau doit suivre : un VPC bien découpé, un filtrage aussi rigoureux qu'au data
center, plusieurs VPC qui communiquent sans devenir un plat de spaghettis, un lien fiable vers le data
center, et le tout décrit en code.

## Au programme

| Chapitre | Ce que vous saurez faire |
|---|---|
| **1. Les bases du réseau AWS** | Découper un VPC en sous-réseaux publics et privés, router vers Internet, comprendre ce qui change par rapport à un LAN |
| **2. Security groups et NACL** | Filtrer avec et sans état, référencer des groupes plutôt que des adresses, dépanner avec les VPC Flow Logs |
| **3. Interconnecter des VPC** | Choisir entre peering, Transit Gateway et PrivateLink, et segmenter avec des tables de routage |
| **4. Le cloud hybride** | Monter un VPN site à site avec BGP, comprendre Direct Connect, maîtriser le chemin emprunté |
| **5. Le réseau en code avec Terraform** | Décrire tout le réseau en code, gérer l'état, et déployer par un pipeline |

Les exemples sont pris sur **AWS**, le plus répandu. Chaque chapitre signale les équivalents **Azure** et
**Google Cloud** : les noms changent, les principes restent.

## Le lab : du Terraform, pas du ContainerLab

Un VPC ne s'émule pas dans un conteneur : le lab de ce saut est un ensemble de fichiers
<Term id="iac">Terraform</Term> qui construit un vrai réseau dans **votre compte AWS**. Il est conçu pour
coûter zéro par défaut : VPC, sous-réseaux, tables de routage, Internet Gateway, security groups et NACL ne
sont pas facturés.

```bash title="Récupérer le lab"
mkdir cloud-aws && cd cloud-aws
for f in versions.tf variables.tf vpc.tf security.tf vpn.tf outputs.tf terraform.tfvars.example; do
  curl -fsSL -o "$f" "https://nexthop.alcpt.network/labs/cloud-aws/$f"
done
```

<Callout type="warning">
Certaines ressources sont **facturées à l'heure**, qu'elles servent ou non : la NAT Gateway, les
attachements de Transit Gateway, les connexions VPN, et chaque adresse IPv4 publique. Comptez de l'ordre de
quelques centimes de dollar par heure et par ressource, soit plusieurs dizaines de dollars par mois si on
les oublie. Dans le lab, elles sont désactivées par défaut (`enable_nat_gateway`, `enable_vpn`…). Activez-les
le temps d'un exercice, puis lancez **toujours** `terraform destroy` en fin de séance. Créez aussi une
**alerte de budget** (*Billing > Budgets*) dès l'ouverture du compte, et vérifiez les conditions de l'offre
gratuite sur la page *AWS Free Tier* : elles évoluent régulièrement.
</Callout>
