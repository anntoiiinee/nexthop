Les chapitres précédents nous ont donné des réseaux bien découpés : des VLAN, chacun avec son
sous-réseau IP. Il reste à les **relier entre eux** et au siège. C'est le travail du routeur,
et c'est d'ailleurs lui qui a donné son nom à ce site : à chaque étape, un routeur ne connaît
pas tout le chemin, seulement **le prochain saut**, le *next hop*.

## Le réseau de l'exemple

## Côté machine : la passerelle par défaut

Avant même d'envoyer un paquet, PC1 se pose une question : **la destination est-elle dans mon
réseau ?** Il applique son masque à sa propre adresse et à celle de la destination :

- `192.168.10.10/26` → réseau **192.168.10.0** ;
- `172.16.20.10` avec le même masque → réseau 172.16.20.0 : **ce n'est pas mon réseau**.

La règle est simple :

1. **même réseau** → il envoie la trame directement à la machine de destination ;
2. **autre réseau** → il envoie la trame à sa **passerelle par défaut** (192.168.10.1, R1), qui
   se chargera de la suite.

Dans les deux cas, il lui faut l'**adresse MAC** du prochain équipement. Il la demande avec
<Term id="arp" />, détaillé au [chapitre précédent](/formations/fundamentals/arp) :

<Callout type="warning">
Une passerelle oubliée ou fausse est l'erreur la plus fréquente sur un poste ou un serveur : la
machine joint parfaitement son propre réseau, mais rien au-delà. Premier réflexe : `ip route`
(Linux) ou `ipconfig` (Windows).
</Callout>

## La table de routage

Un routeur décide où envoyer chaque paquet grâce à sa **table de routage** : une liste de
réseaux de destination, avec pour chacun l'interface de sortie et le prochain saut.

Au démarrage, R1 connaît seulement ses réseaux **directement connectés** : ceux de ses interfaces.

```text title="R1#show ip route"
VRF: default
Codes: C - connected, S - static, K - kernel, B - BGP, O - OSPF

Gateway of last resort is not set

 C        192.168.10.0/26 is directly connected, Ethernet1
 C        192.168.10.120/31 is directly connected, Ethernet2
```

Le réseau du siège n'y figure pas : un paquet vers 172.16.20.10 serait **jeté**. Pour qu'il le
connaisse, deux solutions : le lui dire à la main (**routage statique**), ou le lui faire apprendre
par un protocole (**routage dynamique** : OSPF, BGP… dans la formation suivante).

## Configurer une route statique

Une route statique se résume à : « pour aller vers **ce réseau**, envoie au **prochain saut** ».

```text title="Arista EOS"
ip route 172.16.20.0/24 192.168.10.121
```

```text title="Cisco IOS"
ip route 172.16.20.0 255.255.255.0 192.168.10.121
```

Le prochain saut doit être **joignable directement**, sur un réseau connecté : ici, l'adresse de
R2 sur le lien R1-R2.

## La route par défaut

R1 est un routeur d'agence : tout ce qui n'est pas local part vers R2. Plutôt que d'écrire une
route par réseau du siège, on utilise la **route par défaut**, `0.0.0.0/0`, qui correspond à
**toutes** les destinations :

```text title="R1 · Arista EOS"
ip route 0.0.0.0/0 192.168.10.121
```

C'est l'équivalent de la passerelle par défaut d'un PC, mais pour un routeur. Elle apparaît comme
**Gateway of last resort** dans la table.

## Le plus long préfixe gagne

Une destination peut correspondre à plusieurs routes. Imaginons cette table sur R2, et un paquet
pour **172.16.20.10** :

| Route | Correspond à 172.16.20.10 ? | Longueur |
|---|---|---|
| `0.0.0.0/0` via 10.0.23.1 | oui (toutes les adresses) | 0 bit |
| `172.16.0.0/16` via 10.0.23.1 | oui | 16 bits |
| `172.16.20.0/24` via 10.0.23.1 | oui | **24 bits** ✓ |
| `172.16.30.0/24` via 10.0.23.1 | non | |

Le routeur choisit **la route la plus précise**, celle qui a le préfixe le plus long : le /24.
La route par défaut ne sert donc que lorsqu'**aucune autre route** ne correspond.

<Callout type="tip">
Cette règle est fondamentale et vaut pour tous les protocoles : statique, OSPF, BGP. Elle permet
par exemple d'avoir une route large vers tout le siège (`172.16.0.0/16`) et une exception plus
précise vers un site particulier.
</Callout>

## Saut par saut : le next hop

Ajoutons les routes nécessaires sur chaque routeur :

```text title="R1"
ip route 0.0.0.0/0 192.168.10.121           ! tout le reste : vers R2
```

```text title="R2"
ip route 192.168.10.0/24 192.168.10.120     ! l'agence : vers R1
ip route 172.16.20.0/24 10.0.23.1           ! le siège : vers R3
```

```text title="R3"
ip route 192.168.10.0/24 10.0.23.0          ! l'agence : vers R2
```

Sur R2, une seule route `/24` couvre **tous** les réseaux de l'agence (utilisateurs, Wi-Fi,
serveurs…) : c'est l'intérêt d'avoir tiré tous les sous-réseaux VLSM d'un même bloc.

Suivons maintenant le paquet. Chaque routeur décide **seul**, sans connaître le chemin complet :

## Le piège du retour

Un ping, c'est un aller **et un retour**. La réponse de l'application part de 172.16.20.10 vers

<Callout type="field">
« Le ping ne passe pas, pourtant ma route est bonne » : neuf fois sur dix, c'est la **route retour**
qui manque, sur un routeur ou sur un firewall du chemin. Vérifiez les deux sens, à chaque saut.
</Callout>

## Les routes flottantes

On peut configurer **deux routes vers la même destination**, par exemple un lien principal et un
lien de secours 4G. Pour les départager, chaque source de routes a une **distance administrative**
(AD) : la plus faible l'emporte.

| Source | Distance administrative (Cisco) |
|---|---|
| Réseau connecté | 0 |
| Route statique | 1 |
| eBGP | 20 |
| OSPF | 110 |
| iBGP | 200 |

<Callout type="note">
Ces valeurs sont celles de Cisco. Elles varient selon les constructeurs : sur Arista EOS, par
exemple, BGP utilise 200 par défaut pour eBGP comme pour iBGP. L'important est le principe :
à préfixe égal, la plus petite distance gagne.
</Callout>

Une **route flottante** est une route statique à laquelle on donne volontairement une distance
plus élevée. Elle reste en réserve, et n'apparaît dans la table que si la route principale disparaît :

```text title="R1 · Arista EOS"
ip route 0.0.0.0/0 192.168.10.121          ! principale, AD 1
ip route 0.0.0.0/0 192.0.2.1 250           ! secours 4G, AD 250 : utilisée seulement si la principale tombe
```

## Dépanner

Trois commandes couvrent l'essentiel :

- `show ip route` (ou `show ip route 172.16.20.10`) : le routeur a-t-il une route, laquelle ?
- `ping` : la destination répond-elle ? Utilise <Term id="icmp" />.
- `traceroute` : par quels routeurs passe-t-on, et où ça s'arrête ?

`traceroute` exploite le TTL : il envoie des paquets avec un TTL de 1, puis 2, puis 3… Chaque
routeur qui fait tomber le TTL à 0 renvoie un message d'erreur ICMP, ce qui révèle son adresse :

```text title="pc1:~# traceroute 172.16.20.10"
traceroute to 172.16.20.10 (172.16.20.10), 30 hops max, 46 byte packets
 1  192.168.10.1 (192.168.10.1)  0.512 ms  0.271 ms  0.236 ms
 2  192.168.10.121 (192.168.10.121)  0.874 ms  0.611 ms  0.583 ms
 3  10.0.23.1 (10.0.23.1)  1.102 ms  0.947 ms  0.902 ms
 4  172.16.20.10 (172.16.20.10)  1.215 ms  1.033 ms  1.011 ms
```

Si la trace s'arrête à un saut (des `* * *`), le problème se situe souvent sur ce routeur ou juste après :
route manquante à l'aller, ou au retour. Souvent, mais pas toujours : le chapitre
[Traceroute](/formations/fundamentals/traceroute) explique pourquoi une trace peut mentir.

## À retenir

- Une machine envoie directement si la destination est **dans son réseau**, sinon à sa **passerelle**.
- Un routeur choisit la route avec le **plus long préfixe** ; `0.0.0.0/0` est la route par défaut.
- Chaque routeur ne connaît que **le prochain saut** : les MAC changent à chaque saut, les IP non.
- Toujours penser à la **route retour**.
- La **distance administrative** départage les sources de routes ; une route flottante sert de secours.

Les paquets savent maintenant aller d'une machine à l'autre. Dernière étape : comprendre comment les
applications s'en servent, avec **TCP et UDP**, la couche transport.
