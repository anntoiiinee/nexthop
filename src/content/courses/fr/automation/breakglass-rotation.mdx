Sur beaucoup de réseaux, on se connecte encore aux équipements avec **le même compte local pour
tout le monde**, souvent nommé `admin`, avec un mot de passe qui n'a pas changé depuis des années.
C'est l'une des failles les plus courantes, et l'une des plus simples à corriger. Ce chapitre met en
place la bonne pratique, et l'automatise.

## Pourquoi le compte admin partagé est un problème

- **Son nom est connu** : `admin`, `cisco`, `root`… Les robots qui balayent Internet et les attaquants
  déjà dans le réseau essaient ces comptes en premier. Il ne leur reste qu'à deviner le mot de passe.
- **Son mot de passe est partagé** : tout le monde le connaît, il circule dans des fichiers, des
  messages, des documentations.
- **Il n'y a aucune traçabilité** : quand `admin` a supprimé un VLAN à 3 h du matin, impossible de
  savoir qui était derrière.
- **Il survit aux départs** : un collègue qui quitte l'entreprise le connaît toujours. Le changer à la
  main sur des centaines d'équipements, personne ne le fait vraiment.

## Le modèle cible

On sépare clairement trois usages :

| Usage | Compte | Où il est défini |
|---|---|---|
| Le travail quotidien des ingénieurs | un **compte nominatif** par personne, avec MFA | serveur <Term id="tacacs" /> ou RADIUS (<Term id="aaa" />) |
| L'automatisation (sauvegardes, déploiements) | un **compte de service**, aux droits limités | serveur TACACS+ |
| Le dernier recours, si les serveurs AAA sont injoignables | **un compte local de secours** (*break-glass*), un mot de passe **unique par équipement** | sur l'équipement, mot de passe dans un **coffre** |

Côté équipement, la configuration AAA s'appuie sur TACACS+ et ne bascule sur les comptes **locaux**
que si aucun serveur ne répond :

```text title="Arista EOS : TACACS+ d'abord, comptes locaux en secours"
tacacs-server host 192.0.2.50 key <clé-partagée>
tacacs-server host 192.0.2.51 key <clé-partagée>
!
aaa group server tacacs+ TACACS
   server 192.0.2.50
   server 192.0.2.51
!
aaa authentication login default group TACACS local
aaa authorization exec default group TACACS local
aaa authorization commands all default group TACACS local
aaa accounting commands all default start-stop group TACACS
```

<Callout type="note">
`local` n'est consulté que si **aucun serveur TACACS+ ne répond**. Un utilisateur refusé par TACACS+
n'est pas réessayé en local : un ancien collègue dont le compte TACACS+ est supprimé ne peut donc pas
se rabattre sur un compte local… à condition qu'il n'en connaisse aucun. D'où l'importance du compte
de secours unique et de sa rotation.
</Callout>

## Les règles du compte de secours

1. **Un nom non devinable**, propre à l'entreprise, jamais `admin`. Le lab utilise `nh-breakglass`.
2. **Un mot de passe long et aléatoire** (32 caractères), **différent sur chaque équipement** :
   un mot de passe compromis n'ouvre qu'une seule porte.
3. **Personne ne le connaît par cœur** : il est généré par un script et stocké dans un **coffre**,
   [HashiCorp Vault](/formations/automation/vault), dont chaque consultation est journalisée.
4. **Une rotation régulière** : **tous les 4 mois**.
5. **Une rotation immédiate** :
   - au **départ d'un membre de l'équipe** qui avait accès au coffre ;
   - **après chaque utilisation** du compte (le mot de passe a été vu) ;
   - au moindre doute de compromission.

## Supprimer le compte admin… sans s'enfermer dehors

Supprimer `admin` en premier, c'est risquer de perdre tout accès si le compte de secours ne fonctionne
pas. L'**ordre des opérations** est donc essentiel, et nos scripts le respectent strictement :

Trois précautions rendent l'opération sûre :

- **Le mot de passe est mis au coffre avant d'être appliqué** (étape 2). Si le script plante juste
  après avoir changé un équipement, le nouveau mot de passe n'est pas perdu : c'est la dernière version
  du secret dans Vault, au statut `pending`. Et si l'équipement n'a pas été modifié, l'ancien mot de passe
  est la version précédente.
- **La vérification utilise une connexion indépendante**, avec le nouveau mot de passe. On ne se
  contente pas de constater que la commande est passée.
- **Un équipement à la fois** : si quelque chose cloche sur le premier, les autres ne sont pas touchés.

## Le coffre : HashiCorp Vault

Les mots de passe sont rangés dans [HashiCorp Vault](/formations/automation/vault), moteur KV v2, avec **un
secret par équipement** : `secret/netops/breakglass/<équipement>`. Chaque secret contient le nom du compte,
le mot de passe et un **statut** :

| Statut | Signification |
|---|---|
| `pending` | écrit juste avant de modifier l'équipement : il est peut-être appliqué, peut-être pas |
| `active` | appliqué, vérifié par une nouvelle connexion, configuration enregistrée |

Chaque rotation crée donc deux versions par équipement, et Vault garde les précédentes : l'historique montre
quand chaque mot de passe a changé, et par qui.

```bash
vault kv get -field=password secret/netops/breakglass/leaf1   # le mot de passe en cours
vault kv metadata get secret/netops/breakglass/leaf1          # les versions, leurs dates et leurs auteurs
vault kv get -version=5 secret/netops/breakglass/leaf1        # un mot de passe précédent
```

Le script s'authentifie avec l'**AppRole** `netops-rotation`, dont la politique n'autorise qu'à écrire et lire
sous `secret/netops/breakglass/`. Les ingénieurs n'ont qu'un droit de lecture, et chacune de leurs lectures est
journalisée : on sait qui a vu le mot de passe, donc quand il faut le changer.

<Callout type="warning">
Le compte de secours sert quand le réseau est en panne : le coffre doit rester joignable à ce moment-là. Rendez
Vault accessible par le réseau hors bande, en cluster, et gardez une copie hors ligne pour les équipements les plus
critiques (voir [le piège réseau](/formations/automation/vault#le-piège-réseau--le-coffre-pendant-la-panne)).
</Callout>

## La version Python

Le script passe par la classe `VaultClient` présentée au [chapitre précédent](/formations/automation/vault).

```text title="python3 python/rotate_breakglass.py --remove-default-admin"
OK    spine1  (version 2)
OK    leaf1  (version 2)
OK    leaf2  (version 2)
Rotation terminée : les mots de passe sont dans Vault, sous secret/netops/breakglass/.
```

En cas d'échec, le script s'arrête et indique quelle version du secret correspond à quel mot de passe :

```text title="Rotation interrompue sur leaf2"
ÉCHEC leaf2 : Authentication failed
Rotation interrompue sur leaf2. Son nouveau mot de passe est la version 3 de secret/netops/breakglass/leaf2 (statut pending) : il a peut-être été appliqué. Sinon, l'équipement a gardé l'ancien (version 2). Les équipements suivants n'ont pas été modifiés.
```

## La version Ansible

Le playbook suit les mêmes étapes, un équipement à la fois (`serial: 1`) et en s'arrêtant à la première
erreur (`any_errors_fatal: true`). Il écrit dans Vault avec le module `vault_kv2_write` de la collection
`community.hashi_vault`.

<CodeFile lab="netops" file="ansible/rotate_breakglass.yml" />

Quelques détails importants :

- `no_log: true` empêche Ansible d'afficher les mots de passe dans sa sortie et ses journaux ;
- `module_defaults` donne à tous les modules Vault la même connexion : le jeton `VAULT_TOKEN`, ou l'AppRole si
  `VAULT_ROLE_ID` est défini ;
- les tâches Vault et la vérification eAPI tournent sur la machine d'Ansible (`delegate_to: localhost`), pas
  sur l'équipement ;
- le mot de passe ne contient ni espace ni `?` (qui déclenche l'aide de la CLI) ;
- la vérification passe par **eAPI** (`uri`) : c'est une connexion HTTPS totalement indépendante de
  la session SSH qui vient de modifier la configuration.

<Callout type="warning">
Les commandes de configuration peuvent être journalisées, par la comptabilité TACACS+
(`aaa accounting commands`) ou un syslog. EOS enregistre une empreinte du mot de passe dans sa
configuration, mais la commande tapée, elle, peut apparaître en clair dans ces journaux. Vérifiez
comment votre serveur AAA traite ces commandes, et restreignez l'accès aux journaux en conséquence.
</Callout>

## Automatiser : tous les 4 mois et à chaque départ

La rotation tourne dans un pipeline, comme la sauvegarde. Deux déclencheurs :

- une **planification** tous les 4 mois : `0 6 1 1,5,9 *` (le 1er janvier, mai et septembre à 6 h) ;
- un lancement **manuel** depuis l'interface (*Run pipeline*), le jour où un membre de l'équipe part.

```yaml title=".gitlab-ci.yml (job de rotation, à ajouter)"
# Ajouter « security » à la liste des étapes : stages: [backup, security]
rotate-breakglass:
  stage: security
  image: python:3.12-slim
  rules:
    - if: $CI_PIPELINE_SOURCE == "schedule" && $JOB == "rotate-breakglass"
    - if: $CI_PIPELINE_SOURCE == "web"
  before_script:
    - pip install -q -r requirements.txt
  script:
    - python3 python/rotate_breakglass.py --remove-default-admin
```

Le job ne modifie plus le dépôt : les mots de passe vivent dans Vault, pas dans Git. Variables à créer (masquées,
protégées) : `NET_USER`, `NET_PASSWORD`, `VAULT_ADDR`, `VAULT_ROLE_ID` et `VAULT_SECRET_ID`. Mieux encore,
l'authentification JWT décrite au [chapitre précédent](/formations/automation/vault#utiliser-vault-depuis-lautomatisation)
supprime les deux dernières. La planification définit `JOB=rotate-breakglass`, pour ne pas lancer la rotation en
même temps que la sauvegarde nocturne.

### La check-list de départ d'un membre de l'équipe

1. Désactiver son compte nominatif dans l'annuaire et sur le serveur TACACS+.
2. **Lancer le pipeline de rotation** du compte de secours.
3. Ses accès à Vault suivent son compte de l'annuaire (OIDC ou LDAP) : ils tombent avec lui. S'il connaissait un
   `secret_id` d'AppRole ou un jeton, les révoquer et en générer de nouveaux pour les pipelines.
4. Révoquer ses clés SSH, ses jetons d'API et ses accès GitLab.
5. Relire la comptabilité TACACS+ de ses dernières semaines d'activité.

## Dans le lab

1. Déployez le lab et vérifiez que le compte par défaut fonctionne : `ssh admin@172.20.30.12`
   (mot de passe `admin`). C'est exactement le problème.
2. Pointez les scripts vers le Vault du lab : `export VAULT_ADDR=http://172.20.30.70:8200`, puis soit
   `export VAULT_TOKEN=netops-root`, soit, plus réaliste, l'AppRole du chapitre précédent
   (`export VAULT_ROLE_ID=… VAULT_SECRET_ID=…`).
3. Lancez la rotation (Python ou Ansible) avec la suppression du compte admin.
4. Vérifiez : `ssh admin@172.20.30.12` est refusé ; `ssh nh-breakglass@172.20.30.12` fonctionne avec
   le mot de passe lu par `vault kv get -field=password secret/netops/breakglass/leaf1`.
5. Relancez la rotation : les mots de passe changent, l'ancien ne fonctionne plus. Affichez l'historique
   avec `vault kv metadata get secret/netops/breakglass/leaf1`.
6. Lisez le journal d'audit : quelles lectures et quelles écritures la rotation a-t-elle faites ?
7. Bonus : arrêtez leaf2 (`docker stop clab-netops-leaf2`) et relancez. Le script s'arrête sur leaf2 :
   quel est le statut de son secret, et quel mot de passe a-t-il réellement ?

## À retenir

- Le compte `admin` partagé est **connu, partagé, intraçable** et **survit aux départs** : supprimez-le.
- Au quotidien : des **comptes nominatifs** via TACACS+ ; en dernier recours : **un compte local de
  secours**, au nom non devinable, avec un mot de passe **unique par équipement**, rangé dans **Vault**.
- Rotation **tous les 4 mois**, et **immédiatement** au départ d'un collègue ou après chaque usage.
- L'ordre est vital : **créer et vérifier le compte de secours avant de supprimer admin**, et mettre le
  nouveau mot de passe au coffre **avant** de l'appliquer (`pending`), puis le valider (`active`).
- Les **versions** de Vault gardent l'ancien mot de passe en cas d'échec, et son **journal d'audit** dit qui a lu
  quoi.
- Un pipeline planifié et déclenchable à la main rend la rotation **systématique**, pas héroïque.
