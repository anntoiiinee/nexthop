Avec Python, on écrit **comment** faire : se connecter, taper telle commande, lire la sortie.
Avec **Ansible**, on décrit plutôt **ce qu'on veut obtenir** (« ces VLAN doivent exister sur ces
leafs ») et Ansible se charge de comparer avec l'existant et de n'appliquer que la différence. C'est
l'outil le plus répandu pour automatiser un réseau d'entreprise.

## Comment fonctionne Ansible

- **Sans agent** : rien à installer sur les équipements. Ansible tourne sur un **nœud de contrôle**
  (votre machine, un runner de CI) et se connecte en SSH ou par API.
- **Un inventaire** liste les équipements et les regroupe.
- **Des playbooks** en YAML enchaînent des **tâches** ; chaque tâche appelle un **module**.
- **Des collections** apportent les modules propres à chaque constructeur : `arista.eos`,
  `cisco.ios`, `junipernetworks.junos`…

<Callout type="note">
Sur un serveur Linux, Ansible copie un petit programme Python sur la machine et l'exécute. Sur un
switch, c'est impossible : les modules réseau tournent donc **sur le nœud de contrôle**, et la
connexion `network_cli` envoie les commandes en SSH. C'est ce que précise `ansible_connection`.
</Callout>

## L'idempotence

C'est la notion centrale d'Ansible. Une tâche <Term id="idempotence">idempotente</Term> décrit un
**état** : elle ne modifie l'équipement que s'il n'est pas déjà dans cet état. On peut donc relancer
un playbook autant de fois qu'on veut, sans effet de bord.

Les VLAN voulus sont décrits dans un fichier de variables, séparé du playbook :

Avant d'appliquer, on demande à Ansible ce qu'il **ferait**, en mode simulation (`--check`).
Avec `-v`, les modules ressources affichent la liste des commandes qu'ils enverraient :

```text title="ansible-playbook ansible/vlans.yml --check -v (extrait)"
TASK [Configurer les VLAN] *****************************************************
changed: [leaf1] => {"before": [{"name": "default", "state": "active", "vlan_id": 1}],
                     "commands": ["vlan 10", "name USERS", "vlan 20", "name GUEST-WIFI",
                                  "vlan 30", "name SERVERS"], ...}
```

Ajouter `--diff` montre en plus l'état avant et après. La présentation exacte varie selon la version
de la collection, mais l'idée reste la même : on voit **avant** d'appliquer.

| Exécution | Résultat | Pourquoi |
|---|---|---|
| `--check` | `changed`, mais rien n'est appliqué | simulation : on voit les commandes qui seraient envoyées |
| 1ʳᵉ exécution | `changed=1` sur chaque leaf | les VLAN n'existaient pas, ils sont créés |
| 2ᵉ exécution | `changed=0` | l'état voulu est déjà atteint : rien à faire |

<Callout type="tip">
`--check --diff` est le meilleur réflexe avant tout changement en production : il montre exactement
ce qui va changer. Dans un pipeline, on l'exécute sur la demande de fusion (merge request), et on
n'applique qu'après relecture.
</Callout>

## Les modules à connaître

| Module | Rôle | Idempotent ? |
|---|---|---|
| `eos_facts` | collecter des informations (modèle, version, interfaces…) | lecture seule |
| `eos_command` | exécuter des commandes `show` | lecture seule (en principe) |
| `eos_config` | envoyer des lignes de configuration, ou un gabarit <Term id="jinja" /> | oui, en comparant avec la running-config |
| `eos_vlans`, `eos_interfaces`, `eos_l3_interfaces`, `eos_bgp_global`… | **modules ressources** : décrire une fonction sous forme de données | oui, avec `state` : `merged`, `replaced`, `overridden`, `deleted` |

Les **modules ressources** sont à privilégier : on manipule des données (une liste de VLAN), pas des
lignes de CLI, et le paramètre `state` dit précisément quoi faire de l'existant. Par exemple,
`overridden` supprime les VLAN qui ne sont **pas** dans la liste : l'équipement devient le reflet
exact des données.

## Protéger les secrets : Ansible Vault

Nos identifiants viennent de variables d'environnement. Pour stocker des secrets avec le code (mots de passe, clés
TACACS+, communautés SNMP), Ansible fournit **Ansible Vault**, qui chiffre en AES-256 avec un mot de passe. Un
contenu chiffré peut être commité dans Git : sans ce mot de passe, il est illisible.

### Les commandes

| Commande | Ce qu'elle fait |
|---|---|
| `ansible-vault create fichier.yml` | crée un fichier chiffré et l'ouvre dans l'éditeur |
| `ansible-vault edit fichier.yml` | déchiffre en mémoire, ouvre l'éditeur, rechiffre à la fermeture |
| `ansible-vault view fichier.yml` | affiche le contenu déchiffré, sans rien écrire sur le disque |
| `ansible-vault encrypt` / `decrypt fichier.yml` | chiffre ou déchiffre un fichier existant, sur place |
| `ansible-vault encrypt_string 'valeur' --name variable` | chiffre une seule valeur, à coller dans un fichier de variables en clair |
| `ansible-vault rekey fichier.yml` | change le mot de passe d'un fichier chiffré |

### Un fichier entier, ou une seule variable

On peut chiffrer **tout un fichier** de variables, ou **une seule valeur** avec `encrypt_string` :


La seconde approche garde le reste du fichier lisible, et ses différences dans Git. Pour un fichier entier, la
convention est de séparer les secrets de leur usage :

```yaml title="group_vars/eos/vault.yml (chiffré)"
vault_tacacs_key: s3cr3t
```

```yaml title="group_vars/eos/vars.yml (en clair)"
tacacs_key: "{{ vault_tacacs_key }}"
```

Un `grep tacacs_key` sur le dépôt trouve ainsi la variable, et le préfixe `vault_` dit où elle est définie.

### Plusieurs coffres : les identifiants de coffre

Un même mot de passe pour le lab et la production, c'est donner la production à tous ceux qui touchent au lab.
Les **identifiants de coffre** (`--vault-id label@source`) permettent d'utiliser un mot de passe par environnement.
Le label est écrit dans l'en-tête du contenu chiffré (`$ANSIBLE_VAULT;1.2;AES256;prod`), et un playbook peut en
recevoir plusieurs :

```bash
ansible-vault encrypt --vault-id dev@~/.vault/dev.pass group_vars/lab/vault.yml
ansible-vault encrypt --vault-id prod@~/.vault/prod.pass group_vars/prod/vault.yml
ansible-playbook site.yml --vault-id dev@~/.vault/dev.pass --vault-id prod@prompt
ansible-vault rekey --vault-id prod@~/.vault/prod.pass --new-vault-id prod@prompt group_vars/prod/vault.yml
```

La source est un fichier de mot de passe, ou `prompt` pour le saisir. Avec un mauvais mot de passe, le message est
explicite :

```text title="ansible-vault view avec un mauvais mot de passe"
[ERROR]: Failed to view 'dev.yml': Decryption failed (no vault secrets were found that could decrypt).
```

### Où ranger le mot de passe du coffre

- **Sur un poste** : un fichier hors du dépôt, lisible par vous seul (`chmod 600`), désigné par `--vault-id` ou par
  la variable `ANSIBLE_VAULT_PASSWORD_FILE`. Ajoutez son nom au `.gitignore` par précaution.
- **Dans un pipeline GitLab** : une variable masquée et protégée de type **File**. GitLab écrit son contenu dans un
  fichier temporaire et met le **chemin** dans la variable : `--vault-id prod@$VAULT_PASS_PROD`.
- **Jamais** dans le dépôt, ni dans `ansible.cfg`, ni en argument de commande visible dans l'historique.

### Le piège : un secret rechiffré… écrit en clair

<Callout type="warning">
Le filtre `ansible.builtin.vault` chiffre une valeur dans un template. Mais ce chiffrement ne survit pas toujours à
l'écriture : avec ansible-core 2.21, une valeur passée par ce filtre puis écrite avec `copy` et `content:` est
**déchiffrée** au moment de l'écriture, et le fichier contient le secret **en clair**. Le playbook se termine sans
erreur. Pour produire un fichier chiffré, passez par `ansible-vault` lui-même, et vérifiez le résultat.
</Callout>

```yaml title="Écrire un fichier chiffré, puis vérifier qu'il l'est vraiment"
- name: Chiffrer avec ansible-vault, le contenu passant par l'entrée standard
  ansible.builtin.command:
    cmd: ansible-vault encrypt --vault-id prod@{{ vault_pass_file }} --output {{ secrets_file }} -
    stdin: "{{ new_secrets | to_nice_yaml }}"
  no_log: true
  changed_when: true

- name: Lire le fichier tel qu'il est sur le disque (slurp ne déchiffre pas)
  ansible.builtin.slurp:
    src: "{{ secrets_file }}"
  register: written

- name: Vérifier que le fichier écrit est bien chiffré
  ansible.builtin.assert:
    that: (written.content | b64decode).startswith('$ANSIBLE_VAULT')
    fail_msg: "{{ secrets_file }} n'est pas chiffré : ne le commitez pas"
```

Pour la vérification, utilisez `slurp`, pas le lookup `file` : ce dernier **déchiffre** automatiquement un fichier
chiffré dont il connaît le mot de passe, et le test échouerait sur un fichier pourtant correct.

### Les bonnes pratiques

- **Aucun secret en clair dans Git**, même dans un dépôt privé : un dépôt finit toujours par être cloné, copié ou
  rendu public. Un secret commité par erreur est compromis : changez-le, nettoyer l'historique ne suffit pas.
- **Un coffre par environnement** (lab, préproduction, production), avec des mots de passe différents.
- **Le moindre privilège** : le compte de service des playbooks n'a que les droits dont il a besoin.
- **`no_log: true`** sur toute tâche qui manipule un secret, pour qu'il n'apparaisse ni dans la sortie ni dans les
  journaux.
- **Une rotation** : `rekey` du coffre au départ de quelqu'un qui en connaissait le mot de passe, et changement des
  secrets eux-mêmes s'il a pu les lire.

Ansible Vault reste un fichier protégé par **un seul mot de passe partagé**, sans trace de qui l'a lu. Au chapitre 4,
on passe à un vrai coffre-fort de secrets, **HashiCorp Vault**, avec des droits par personne et un journal de chaque
lecture.

## Python ou Ansible ?

| | Python | Ansible |
|---|---|---|
| Approche | impérative : on écrit les étapes | déclarative : on décrit l'état voulu |
| Idempotence | à programmer soi-même | fournie par les modules |
| Logique complexe, calculs, API diverses | très à l'aise | vite laborieux |
| Lisibilité pour l'équipe | demande de savoir coder | YAML lisible par tous |
| Usage typique | outils sur mesure, collecte de données, intégrations | déploiement de configurations, opérations répétitives |

Les deux se complètent : beaucoup d'équipes déploient avec Ansible et écrivent en Python les outils
autour (rapports, contrôles, intégrations avec NetBox). Les deux chapitres suivants proposent chaque
script dans les deux versions.

## À retenir

- Ansible est **sans agent** : pour le réseau, les modules tournent sur le nœud de contrôle (`network_cli`).
- **Inventaire** + **group_vars** + **playbooks** ; les **collections** apportent les modules constructeur.
- L'**idempotence** : décrire un état, n'appliquer que la différence ; `--check --diff` avant d'appliquer.
- Privilégiez les **modules ressources** et leur paramètre `state`.
- Les secrets vont dans **Ansible Vault** (ou un vrai coffre), jamais en clair dans le dépôt : un coffre par
  environnement avec `--vault-id`, et une vérification que tout fichier écrit commence par `$ANSIBLE_VAULT`.
